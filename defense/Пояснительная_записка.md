# Разработка системы автоматизированной проверки технической документации с применением локальной языковой модели

Автор: Морсин Арсений, 10А, лицей №393.

## 1. Введение. Цель и задачи

Специалисты Горэлектротранса проверяют объёмные отчёты подрядчиков по договору и техническому заданию. В исходном описании задачи фигурирует отчёт примерно на 500 страниц. Ручной поиск оснований требует внимания и времени, а конфиденциальность материалов ограничивает возможность использовать облачные сервисы [1].

Проблема проекта — как помочь специалисту находить подтверждения и явные расхождения по готовому перечню требований, сохраняя документы на его компьютере. Целевая аудитория — сотрудники, выполняющие содержательную проверку технической документации.

Цель работы — разработать локальное настольное приложение, которое принимает DOCX или текстовый PDF и готовый чек-лист, формирует таблицу предварительных выводов с цитатами и адресами и сохраняет её в Excel.

Для достижения цели поставлены задачи: определить границы проверки; реализовать извлечение текста с сохранением адресов; организовать смысловой поиск; подключить локальную языковую модель; проверять подлинность цитат; создать интерфейс и экспорт; провести испытания и подготовить документацию.

Работа является практическим проектом. Основной результат — действующее приложение. Гипотеза исследовательской работы не выдвигалась. Решение по каждому пункту принимает специалист; программа предоставляет основания для его работы.

## 2. Выбор подхода и технологий

Проверка всего большого документа за один запрос требует значительного контекста. Поиск только по словам пропускает переформулированные сведения. Выбран подход RAG: сначала программа подбирает релевантные фрагменты, затем передаёт модели одно требование и найденный контекст.

Для смыслового поиска используется multilingual-e5-small с локальными ONNX-весами. Фрагменты получают префикс passage:, требования — query:. Векторы вычисляются с masked mean pooling и нормализацией L2. Учитывается ограничение модели в 512 токенов [2]. Совпадения обозначений оборудования и номеров пунктов дополняют смысловой поиск.

Исходный кандидат Qwen2.5 3B оказался недостаточно точным на учебных примерах. Для рабочего профиля выбрана Qwen2.5 7B Instruct в формате GGUF Q4_K_M [3]. Модель выполняется процессом llama.cpp, доступным только через локальный адрес [4]. Запрос ограничен схемой JSON; программа дополнительно проверяет полученный ответ.

По предложению автора проверена базовая mDeBERTa из прежнего проекта. Компактный чекпоинт без дообученного адаптера дал четыре правильные метки на пяти диагностических парах. Обнаружены отсутствующие токены чисел и обозначений. Этот эксперимент не равнозначен испытанию полного исходного NLI-чекпоинта [6].

Интерфейс реализован на Python и PySide6 [5]. Использованы python-docx, pypdf, NumPy, ONNX Runtime, tokenizers, httpx и openpyxl. Такое разделение позволяет проверять содержательную логику без запуска окна и заменять адаптер модели независимо от интерфейса.

## 3. Архитектура и обработка данных

Архитектура разделена на предметную область, сценарии приложения, адаптеры и представление. Предметная область описывает требование, текстовый блок, источник, доказательство, содержательный результат и техническую ошибку. Её структуры неизменяемы и не зависят от Qt, HTTP и библиотек чтения файлов.

Из DOCX извлекаются основной текст и строки таблиц в порядке документа. Для таблиц сохраняются название, заголовки столбцов и отдельные ячейки; модель получает их сгруппированными в JSON. Адрес включает путь заголовков, номер абзаца либо таблицы и строки. Из PDF извлекается текст каждой страницы с предупреждениями о недоступном тексте.

Большие блоки делятся на фрагменты примерно по 400 токенов с перекрытием 50. Матрица векторов документа рассчитывается один раз. Для требования выбирается до восьми фрагментов с учётом смысла и обозначений. Модель не получает весь большой документ.

Для определённого вывода необходимы доказательства. Цитата сверяется именно с переданным фрагментом; при сравнении нормализуются только пробелы и переносы. При неподтверждённой цитате вывод становится неопределённым. Адрес подставляется из данных программы. Сам факт совпадения цитаты не гарантирует верную интерпретацию её смысла.

## 4. Реализация и пользовательский сценарий

Пользователь выбирает отчёт и CSV-чек-лист с колонками id и requirement. После проверки входных данных приложение загружает локальные веса, строит индекс и последовательно проверяет пункты. Результаты появляются в таблице; выбранная строка раскрывает пояснение, цитаты и источники.

В интерфейсе предусмотрены фильтры статусов, прогресс и отмена. Рабочий поток владеет моделями и индексом, а окно получает результаты сигналами Qt. При отмене завершается текущая операция; тайм-аут ограничивает ожидание модели. Технический сбой не превращается в вывод о содержании отчёта.

Excel содержит листы результатов, доказательств и сведений. Сохраняются все использованные цитаты. Запись выполняется через временный файл с заменой результата после успешного сохранения. Пользовательский текст в ячейках защищён от интерпретации как формулы.

## 5. Испытания и анализ результатов

Подготовлен десятистраничный учебный отчёт об испытаниях ТК-101 в DOCX и PDF и подробный чек-лист из 32 требований. Он содержит 18 подтверждений, 8 противоречий и 6 случаев недостатка данных. Ожидаемые ответы приведены в examples/expected.json для ручного сопоставления [7].

Основная приёмка предусматривает запуск приложения на документе и чек-листе куратора с построчной сверкой выводов и цитат. Эти материалы ещё не получены; апробация у индустриального партнёра не заявляется. Учебный пример не заменяет такую приёмку.

Для устранения неоднозначности таблиц DOCX модель получает название таблицы, заголовки столбцов и выбранные строки с отдельными ячейками. Модель выбирает ID ячеек, приложение подставляет их исходный текст; JSON-схема ограничивает ID источниками запроса. На прежнем примере N04 ошибочно считался неопределённым при фактической редакции 2 вместо 4. После изменения формата получено несоответствие с подтверждённой цитатой. Пояснения запрашиваются строго на русском; смысл выводов требует проверки специалистом.

Скрипты искусственных нагрузочных измерений удалены из рабочего проекта. Оценка времени и качества на реальном объёмном отчёте должна проводиться при приёмке с куратором, с фиксацией оборудования, версии приложения и найденных расхождений.

Регрессионные тесты проверяют адресацию, CSV, доказательства, структурированные ответы, отмену, жизненный цикл процесса, установку компонентов, экспорт и работу интерфейса. Проверка кода не заменяет экспертную оценку правильности выводов модели.

## 6. Выводы и практическая значимость

Создано настольное приложение с полным сценарием: документ и чек-лист → локальный поиск и проверка → таблица с доказательствами → Excel. Реализованы три содержательных статуса, отдельная диагностика технических сбоев и проверка адресов цитирования. Исходный код и воспроизводимые примеры доступны в репозитории [7].

Практическая значимость состоит в сокращении ручного поиска по документу и представлении оснований в единой таблице. Экономия рабочего времени специалиста пока не измерена. Заявлять подтверждённый экономический эффект или внедрение до апробации нельзя.

Текст и ответы остаются на компьютере пользователя. Подготовка зависимостей и загрузка весов требуют интернета; рабочая проверка с подготовленными файлами использует локальный процесс. На компьютерах без подходящего ускорения предусмотрен режим CPU.

Ограничения первой версии: нет OCR, автоматического построения чек-листа и проверки оформления. Не анализируются изображения, текстовые поля, колонтитулы и макросы DOCX. Сложные таблицы, объединённые ячейки и неоднозначные требования нуждаются в ручной проверке. Поиск может пропустить основание, а модель — неверно истолковать найденный фрагмент.

Следующий этап — получить согласованные учебные материалы куратора, отдельно оценить полноту поиска и качество выводов, измерить время специалиста и собрать замечания к интерфейсу. После этого можно рассматривать OCR, дополнительные модели и проверку запуска на Intel Mac.

Автором в рамках проекта выполнены постановка сценария, интеграция библиотек, организация проверки доказательств и испытаний. Используются готовые открытые модели, собственная модель с нуля не обучалась. Разработка выполнялась с помощью ИИ-ассистента; автору необходимо изучить код и проверить материалы перед защитой.
