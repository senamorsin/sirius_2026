# Архитектура

Зависимости направлены к предметной логике. Единственное место, которое выбирает
конкретные реализации и собирает их вместе, — `src/sirius_proj/bootstrap.py`.

```text
cli.py ──► bootstrap.py
              ├─ создаёт ui/window.py, передаёт сервис и экспорт
              ├─ собирает application/ReviewService
              └─ выбирает реализации adapters/

ui/ ───────────► application/ ──► domain/
adapters/ ─────► application/ports.py и domain/
```


## Предметная область — domain

`models.py` описывает неизменяемые требования, текстовые блоки, адреса и результаты.
`TableRow` хранит заголовки, ячейки и название таблицы; блок строки сохраняет точный
исходный текст для проверки цитат. При разбиении длинной строки метаданные ячеек
обрезаются до переданного фрагмента, чтобы не выйти за контекст поиска.
`Finding` запрещает определённый вывод без доказательств; `CheckFailure` представляет
техническую ошибку, а не четвёртый содержательный статус.

`evidence.py` — чистая функция проверки цитат. Она проверяет принадлежность цитаты
именно переданному фрагменту и подставляет адрес из извлечённого текста. Нормализуются
только пробелы и переносы. В этом слое нет JSON, NumPy, Qt, HTTP и доступа к файлам.

## Сценарий — application

`ReviewService` получает четыре зависимости через конструктор: читатели документа
и чек-листа, построитель индекса и фабрику контекстного менеджера модели. Сценарий
не импортирует адаптеры и не выбирает модель. Он управляет этапами, прогрессом,
отменой и временем выполнения. `checks.py` проверяет требования через интерфейсы
`SearchIndex` и `Judge`.

Только ожидаемый `CheckError` адаптера превращается в ошибку пункта. Ошибки
программирования не маскируются продолжением проверки. Входные ошибки чтения и
конфигурации завершают весь запуск с сообщением пользователю.

## Инфраструктура — adapters

- `documents.py`: CSV, основной текст DOCX, строки таблиц и страницы PDF.
- `embeddings.py`, `search.py`: локальный E5, токенизация, одна матрица векторов,
  смысловой поиск, BM25 и частотный вес точных обозначений.
  Частое имя объекта не получает абсолютного приоритета перед нужным параметром.
- `llama_client.py`: протокол HTTP, JSON-схема, запрос и разбор ответа модели.
- `llama_process.py`: запуск, готовность и остановка собственного llama.cpp.
  ExitStack закрывает процесс, HTTP-клиент и временный журнал также при ошибке
  определения GPU или загрузки модели.
- `xlsx.py`: экспорт, предупреждение о частичном результате, защита текстовых ячеек
  от формул и атомарная замена итогового файла.

Параметры моделей и их проверка находятся в `config.py`. Рабочий профиль — Qwen 7B;
автоматического возврата к отклонённой 3B нет.

## Представление — ui

Окно получает фабрику сервиса и функцию сохранения через конструктор. Оно не
импортирует файловые и модельные адаптеры. `CheckWorker` вызывает тот же сценарий,
что и CLI, в рабочем потоке. Модели и индекс принадлежат этому потоку; окно получает
неизменяемые значения сигналами Qt. Общий только флаг отмены `threading.Event`.

`ResultTable` единолично владеет соответствием строк и результатов; окно не ведёт
дублирующий изменяемый список. Отображение доказательств вынесено отдельно.

`startup.py` проверяет нативную зависимость X11 до создания QApplication. На Ubuntu
недостающую libxcb-cursor можно подготовить локально в `runtime/qt` без sudo.
В рабочем режиме не используется подмена платформы на offscreen.

## Проверки границ

`tests/test_architecture.py` запрещает обратные импорты: domain/application не
зависят от инфраструктуры и Qt, а UI не выбирает адаптеры. Поведенческие тесты
используют внедрённые зависимости без подмены внутренних классов сценария.
`tests/test_desktop.py` отдельно запускает CLI на настоящем xcb и проверяет видимое,
показанное оконным менеджером окно. На машинах без DISPLAY этот тест пропускается.

## Передача таблиц и язык

DOCX читается в порядке абзацев и таблиц. Заголовок таблицы распознаётся по разметке
Word или известным именам столбцов. Для неизвестной схемы сохраняются нейтральные
имена «Столбец N». Название берётся из непосредственно предшествующей подписи
«Таблица N». Объединённые ячейки и многоуровневые шапки не реконструируются полностью.

Поиск индексирует строки вместе с заголовками столбцов и названием. Адаптер модели
собирает выбранные строки одной таблицы в JSON:

```json
{
  "tables": [{
    "section": "Комплект документации",
    "caption": "Таблица 3 — Фактически переданные документы",
    "columns": ["Документ", "Редакция"],
    "rows": [{"row": 2, "cells": [
      {"cell_id": "t3r2:cell1", "column": "Документ", "text": "Руководство по эксплуатации"},
      {"cell_id": "t3r2:cell2", "column": "Редакция", "text": "2"}
    ]}]
  }],
  "fragments": []
}
```

Передаются выбранные строки, а не вся таблица. Имя столбца повторяется у каждой
ячейки: модели не нужно восстанавливать связь по индексам двух массивов.
Для таблицы модель возвращает выбранный `cell_id` в поле `evidence.chunk_id`, оставляя
`quote` пустым. Адаптер разрешает только ID переданных ячеек, подставляет их исходный
текст и ID блока строки. JSON-схема ограничивает `evidence.chunk_id` перечислением ID
этого запроса: свободно сгенерировать другой адрес сервер не позволяет. Затем применяется общая проверка цитат. У абзацев остаются обычные
`chunk_id` и дословная цитата. Адрес в обоих случаях подставляет приложение.
Системный промпт объясняет соответствие
столбцов ячейкам, различие факта и требования и требует русское пояснение. При ответе
с иероглифами выполняется одна отдельная попытка перевода пояснения; статус и цитаты
не перегенерируются. Неудача — техническая ошибка пункта.

## Подготовка компонентов

`installation.py` — инфраструктура установки, вызываемая CLI и внедряемой в окно
функцией из `bootstrap.py`. Предметная область и сценарий проверки не знают о сети,
загрузке и установке. `SetupWorker` отделён от `CheckWorker`; окно не допускает
одновременную установку и проверку. Поток получает только путь компонентов, прогресс
и флаг отмены, без документов пользователя.

Установщик закрепляет ревизии весов и runtime, проверяет SHA-256, загружает во временный
файл и заменяет модель после проверки. При повторном запуске исправные файлы используются
повторно; при отмене временный файл удаляется. Системная блокировка разрешает
только одному установщику изменять общий каталог компонентов.
Нативная зависимость X11 подготавливается до создания QApplication. Окно запускает подготовку при отсутствии файлов; повторная
подготовка доступна в настройках. CLI предоставляет подкоманду `install`.

Каталог данных задаётся в `config.py`, отдельно от кода: в checkout — корень проекта,
в установленном/будущем упакованном приложении — пользовательский каталог данных.
Это позволяет хранить загружаемые веса отдельно от будущего исполняемого файла.
Самостоятельный executable в этой версии не собирается.
